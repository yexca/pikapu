# Internationalization

The UI is available in English (`en`) and Simplified Chinese (`zh-Hans`).
English is canonical and the fallback.

## How the Locale Is Chosen

1. The user's preference from **Settings → Language** (`auto`, `en`, or
   `zh-Hans`), stored in `localStorage` under `pikapu-prefs`.
2. For `auto`, the first supported entry in `navigator.languages`:
   `en`/`en-*` → English; `zh`, `zh-CN`, `zh-SG`, `zh-Hans*` → Simplified
   Chinese. Other languages, including Traditional Chinese (`zh-TW`,
   `zh-HK`, `zh-Hant`), are skipped.
3. English if nothing matches.

`resolveLocale` in `frontend/src/i18n/index.ts` implements this, and
`LocaleSync` re-applies it when the preference or the browser language
changes, updating `<html lang>` as well.

## Catalogs

| File | Role |
| --- | --- |
| `src/i18n/locales/en.ts` | Canonical catalog; its shape defines the `Messages` type |
| `src/i18n/locales/zh-Hans.ts` | Typed as `Messages`, so a missing or extra key fails `tsc` |
| `src/i18n/i18next.d.ts` | Makes `t()` keys type-checked |

Keys are grouped by surface (`nav`, `list`, `reader`, `settings`, `errors`,
…). Use the i18next conventions:

- Interpolation: `t("feed.refreshed", { title })` with `{{title}}` in the
  string.
- Plurals: define `key_one` and `key_other` and pass `count`. Chinese has no
  plural forms but must still define both keys to satisfy the type.
- Language names in the language picker are written in their own language
  (`LOCALES` in `src/i18n/index.ts`) and are not translated.

## Using Translations

- In components: `const { t } = useTranslation()`. Memoized components must
  call the hook themselves so they re-render when the language changes.
- Outside components (query hooks, toasts, shadcn primitives):
  `import i18n from "@/i18n"` and call `i18n.t`.
- Dates: `relativeTime()` and `fullTime()` in `src/lib/time.ts` use `Intl`
  with the active locale. Do not hand-format dates.

## Backend Messages

The backend never localizes. Errors are `{"error": "<English>", "code":
"<code>"}` (see [HTTP API](../architecture/api.md#errors)), and a feed's last
failure is stored as `last_error_code` plus the English `last_error`.

The frontend turns them into text with:

- `errorMessage(err)` for `ApiError`s thrown by the API client
- `feedErrorMessage(feed)` for feed update failures

Both look up `errors.<code>` and pass the English message as `{{detail}}`,
falling back to the English message for unknown codes.

## Adding a String

1. Add the key to `en.ts`.
2. Add the translation to `zh-Hans.ts` (`tsc` fails until you do).
3. Use it with `t("group.key")`.
4. Run `make test-frontend`.

## Adding an API Error Code

1. Return it from the handler with
   `writeError(w, status, "my_code", "english message")`.
2. Add `errors.my_code` to both catalogs.
3. Document it in the [error table](../architecture/api.md#errors).
4. Run `make test`.

## Adding a Language

1. Create `src/i18n/locales/<tag>.ts` typed as `Messages`.
2. Register it in `resources`, `supportedLngs`, `LOCALES`, the `Locale` type,
   `resolveLocale`, and `intlLocale` in `src/i18n/index.ts`.
3. Update this page, [Settings](../user/settings.md), and the READMEs.
